## 代码怎么复用

`packages/game` 已经从原型里拆出来：`createGame`（用上传的 28 天历史孵化）、`liveDay`（结算一天）、`fightBoss`、`fightFriend`（打存好的快照，`snapshotOf` 生成快照）、`migrate`（旧存档补字段），还有早晨卡片、通知文案、作息这些纯函数。它不碰浏览器存储、不依赖模拟人设，服务器只需要：读状态 → 调这些函数 → 存回去。有测试覆盖"真实历史、打数据库里存的快照、确定性"。

## 结算怎么触发

- **客户端上传触发，不靠定时任务**：手机每天把前一天的汇总传上来，服务器跑 `processDay` → 遭遇 → 试炼，返回早晨卡片的数据。种子是 `用户ID:日期`，同一天重传结果一样（幂等）。
- 周 Boss：Boss 日上传时生成"待开打"；用户点开打时结算；下一次上传时如果还没打就自动结算。
- 好友快照：每次结算后顺手存一份当天的战斗快照（属性、技能、战术、状态加成），好友来打时读它。
- 推送：结算完成后决定要不要发早上那条（按 [07 §4](07-打磨规范.md) 的优先级和开关）。

## 数据（草图）

`users`（匿名 ID、Apple ID、地区、通知开关）· `pets`（宠物状态 JSON、版本号）· `days`（每天一行汇总 + 结算结果）· `battles`（试炼 / Boss / 切磋的种子和结果，回放可以重算）· `friends`（双向关系）· `snapshots`（好友快照，按天）· `letters` · `subscriptions`。

健康汇总只存一行一天，不存原始记录、不存位置（[03](03-健康数据.md)）。

## 技术栈候选

| | Cloudflare Workers + D1 | Supabase（Postgres + Edge Functions） | Firebase |
|---|---|---|---|
| 跑我们的 TS 引擎 | 可以，Workers 就是 TS/JS | 可以，Edge Functions 是 Deno/TS | 可以，Cloud Functions 是 Node |
| 数据库 | D1（SQLite），免费额度按天给：约 500 万行读、10 万行写、5 GB | Postgres，免费 500 MB；**免费项目闲置会暂停** | Firestore（文档库） |
| Sign in with Apple | 自己验 Apple 的 JWT（不难，要自己写） | 自带 Apple 登录 | 自带 Apple 登录 |
| 推送（APNs） | 要自己用 fetch 调 APNs，**是否顺利需要验证** | 自己写或用第三方 | 有 FCM，iOS 也能转 APNs |
| 成本（早期） | 很低 | 免费层够用，正式上线 $25/月起 | 按量，早期很低 |
| 锁定 | 中 | 低（就是 Postgres） | 高 |

价格数字来自第三方比较站，互相有出入，选定前要看官方价格页（[Cloudflare D1 价格](https://developers.cloudflare.com/d1/platform/pricing/index.md)、[freetier.co 比较](https://freetier.co/compare/cloudflare-d1-vs-supabase)、[bejamas 比较](https://bejamas.com/compare/cloudflare-d1-vs-supabase)）。

**我的倾向：Cloudflare Workers + D1。** 引擎是纯 TS、没有依赖，放进 Worker 最直接；按天结算的读写量很小，免费额度够很久；海外延迟好。要额外做的是 Apple 登录验签和 APNs 推送，这两块先做个小验证。
如果更想少写登录和推送，选 **Supabase** 也合理。

### Cloudflare 那两个"要验证"的点（调研结果）

- **Apple 登录验签**：Workers 里可以用 `jose` 库，从 Apple 的公钥地址 `https://appleid.apple.com/auth/keys` 取公钥（按 token 的 `kid` 找），验签名，再检查 `iss` = `https://appleid.apple.com`、`aud` = 我们的 App ID、`exp`、`nonce`。算法以公钥声明的为准，不从 token 头里读。Cloudflare 自己的文档就是用 `jose` + 远程公钥集验 JWT，只是例子不是 Apple。结论：**可行，工作量小**。（[Apple: Verifying a user](https://developer.apple.com/tutorials/data/documentation/signinwithapple/verifying-a-user.md)、[Kinde: Workers 里验 JWT](https://docs.kinde.com/integrate/third-party-tools/verifying-jwts-cloudflare-workers/)、[Cloudflare: 验证 JWT](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/index.md)、[sarunw 教程](https://sarunw.com/posts/sign-in-with-apple-3/)）
- **APNs 推送**：APNs 要 HTTP/2 + JWT（ES256，用 .p8 私钥签，token 20–60 分钟内复用）。有人专门做了 Workers 能用的版本 `@fivesheepco/cloudflare-apns2`，说明原版 apns2 的依赖在 Workers 里跑不了、这个分支可以。Workers 的 fetch 会自动跟对方协商 HTTP/2，不能强制。结论：**大概率可行，但没找到"已经在生产用"的报告，要先往沙盒环境发一条试试**。（[cloudflare-apns2](https://npmjs.com/package/@fivesheepco/cloudflare-apns2)、[Apple: 与 APNs 通信](https://developer.apple.com/library/prerelease/content/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CommunicatingwithAPNs.html)、[token 有效期](https://www.esegece.com/community/blog/apple-push-notifications-token-based-connections-apns/)）
- 每天只有一条早上推送，量很小；万一 Workers 直连 APNs 不顺，退路是把推送交给一个小的第三方服务。
